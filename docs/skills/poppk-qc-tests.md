# `poppk-qc-tests`

Creates and runs the QC-readiness test suite of a popPK version,
`tests/poppk/v{n}/test-poppk-qc.R`. A version is ready for QC only when this suite passes
with zero failures.

## When it is used

- You ask for QC tests, QC readiness, or "is popPK v{n} ready for QC?".
- It is the last step of every popPK version, after `generate-spec.R`. `run_version()` runs
  it automatically.
- Use neighbouring skills for other tasks:
  - writing the spec the suite checks: [poppk-run-spec](poppk-run-spec.md);
  - NCA suites: [pk-nca-qc-tests](pk-nca-qc-tests.md);
  - simulation suites: [poppk-simulation](poppk-simulation.md) (`run_sim_qc_tests()`).

## What it produces

| File or object | Location | Contents |
|---|---|---|
| `test-poppk-qc.R` | `tests/poppk/v{n}/` | The version's testthat suite, generated from the skill template |
| `qc-tests-{timestamp}.xml` | `output/poppk/v{n}/logs/` | JUnit report of each run: which checks passed or failed |
| Console result | - | "v{n} is ready for QC: all N tests passed", or an error "v{n} is NOT ready for QC" |

`project_status()` (pk-project) reads the latest JUnit report to show each version's QC state.

## How to use it

1. Run the version's scripts first: `analysis-poppk.R`, every `fig-*.R` and `tbl-*.R`,
   then `generate-spec.R`.
2. The suite is generated by `new_version("poppk")`. Generate it yourself only for a
   version created by hand:

   ```r
   source(".posit/assistant/skills/poppk-qc-tests/scripts/poppk_qc_tests.R")
   create_poppk_qc_tests(1L)   # will not overwrite without overwrite = TRUE
   ```

3. Optional: add analysis-specific checks at the end of the suite, under section 9 (for
   example an expected covariate in the final model, or a parameter within a literature
   range).
4. Run it from the project root:

   ```r
   source(".posit/assistant/skills/pk-project/scripts/project.R")
   run_qc("poppk", 1L)
   ```

   or from the shell:

   ```sh
   Rscript -e 'source(".posit/assistant/skills/poppk-qc-tests/scripts/poppk_qc_tests.R"); run_poppk_qc_tests(1L)'
   ```

5. On failure, fix the cause (re-run the stale script, then `generate-spec.R`) and run the
   suite again.

Typical prompts: "Is popPK v1 ready for QC?", "Run the QC tests for popPK v2".

## What the suite checks

| Section | Checks |
|---|---|
| 1. Structure | One `analysis-*.R`, a `generate-spec.R`, at least one `tbl-`/`fig-` script; every `project_number` and `poppk/v{n}/` path points at this version; every script logs to `output/poppk` |
| 2. Logs | Each script's latest log exists, has this `project_number`, reached `nca_log_stop()`, and has no `Error` lines |
| 3. Spec | Sidecar hash matches; project number and script folder; description, dataset, report title, final run, rationale, models and units filled in; `qc.status` is `pending` or `in_review` |
| 4. Provenance | Spec lists exactly the scripts on disk with matching hashes; source data hash; database payload and source hashes match the spec; no stale-data warning; model dataset hash |
| 5. Outputs | Every `tbl-`/`fig-` script has a recorded, non-empty output inside `output/poppk/v{n}/` that matches its hash |
| 6. Model trail | Spec runs equal the stored fits; each run's OFV and model-code hash match its fit; finite OFVs; parents exist; dOFV consistent; exactly one final model, the same in database and spec |
| 7. Final model | The fit used every subject and observation; no acceptance check fails; the spec's recorded checks and caveats equal a recomputation |
| 7b. Fit archives | Every run has an nlmixr2save archive matching its hash; the final model's archive reloads with the same OFV and THETAs; the data-free shared copy exists and has no `origData` (skipped for specs that predate archives) |
| 8. Negative controls | A tampered spec, a modified or missing output and a corrupted database blob are each detected (on temporary copies only) |
| 9. Analysis-specific | Your own checks, added by hand |

The suite loads the fits with `read_poppk_db()` and recomputes the acceptance checks. It
does not refit.

## Main functions and files

| Function or file | Purpose |
|---|---|
| `create_poppk_qc_tests(project_number, tests_dir, overwrite)` | Writes `tests/poppk/v{n}/test-poppk-qc.R` from the template |
| `run_poppk_qc_tests(project_number, tests_dir, output_dir)` | Runs the suite, writes the JUnit report, errors if any test fails |
| `run_qc("poppk", n)` | pk-project wrapper that calls `run_poppk_qc_tests()` |
| `assets/test-poppk-qc-template.R` | The test body; generate from it, do not hand-write the suite |
| `scripts/poppk_qc_tests.R` | The two helpers above |

## Rules and checks

- Ready for QC means the suite passes with zero failures. Quote the result.
- Never weaken or edit a test to make it pass, and never edit the spec by hand.
- Never set `qc.status: approved`. That is the reviewer's sign-off.
- Fix the cause: re-run the stale script, then `generate-spec.R`, then the suite.
- `create_poppk_qc_tests()` refuses to overwrite an existing suite, because it may hold
  hand-added checks.
- popPK suites live in `tests/poppk/v{n}/`, apart from the NCA suites, so version numbers of
  the two types never collide.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| "No tests for v{n}" | The suite does not exist; run `create_poppk_qc_tests(n)` |
| "already exists -- pass overwrite = TRUE" | A suite is already there and may hold your own checks; keep it |
| "model dataset hash matches the spec" fails | The data was read as a lazy `read_csv()` tibble. Read it with `read_csv(..., lazy = FALSE) \|> as.data.frame()` (poppk-estimation rules) |
| Output hash or log checks fail | A script ran after `generate-spec.R`, or failed. Re-run the version with `run_version("poppk", n)` |
| "model code" or OFV mismatch in the trail | The database was rewritten after the spec. Regenerate the spec |
| Acceptance check fails | The final model does not pass `acceptance_checks()`; this is a modelling problem to solve in `poppk-estimation`, not in the test |
